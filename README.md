# ВышКат — система учёта парка

## Описание проекта

«ВышКат» — консольное приложение для учёта транспортных средств и оборудования сервиса аренды. Программа хранит инвентарные объекты, проверяет их перед добавлением в парк и формирует отчёты.

### Возможности

* Добавление самокатов, велосипедов, шлемов и зарядных станций.
* Проверка объектов перед постановкой на баланс.
* Контроль уникальности инвентарных номеров.
* Просмотр общего инвентаря с названиями и номерами объектов.
* Подсчёт количества объектов.
* Расчёт суммарного суточного энергопотребления.
* Формирование списка транспорта для новичков с уровнем простоты от 6 до 10.
* Демонстрация отказа техосмотра в специальном режиме.

## Требования

* Go версии, совместимой с версией, указанной в `go.mod`.
* Зависимость Uber Fx для внедрения зависимостей.

Установка зависимостей:

```bash
go mod tidy
```

## Запуск

Обычный режим:

```bash
go run ./cmd/vyshkat
```

Режим демонстрации отказов техосмотра:

```bash
go run ./cmd/vyshkat -demo-rejection
```

В демонстрационном режиме объекты с инвентарными номерами, начинающимися с `FAIL-`, отклоняются.

## Структура проекта

* `domain/` — предметные сущности и интерфейсы.
* `service/` — реестр объектов, бизнес-логика парка и техосмотр.
* `app/` — консольный интерфейс.
* `di/` — сборка приложения и внедрение зависимостей через Uber Fx.
* `cmd/vyshkat/` — точка входа программы.

## Архитектурные решения

### Единый реестр

Транспорт и оборудование хранятся в одном реестре. Каждый объект реализует интерфейс `InventoryItem`, предоставляющий название и инвентарный номер.

Для объектов, потребляющих энергию, предусмотрен интерфейс `EnergyConsumer`. Транспорт реализует интерфейс `Transport`, включающий уровень простоты для новичка.

Это позволяет формировать отчёты без привязки к конкретным типам объектов.

### Технический осмотр

Перед добавлением объекта `FleetService` вызывает метод `Inspect` зависимости, реализующей `InspectionService`.

В обычном режиме используется заглушка, которая принимает все объекты. В демонстрационном режиме используется альтернативная реализация, позволяющая проверить сценарий отказа.

Если техосмотр не пройден, объект не попадает в реестр.

### Внедрение зависимостей

Uber Fx собирает зависимости приложения. Реализации интерфейсов предоставляются контейнером, а не создаются непосредственно в консольном интерфейсе.

Это уменьшает связанность компонентов и упрощает замену реализаций, например при тестировании.

## Применение SOLID

* **S — Single Responsibility Principle.** Предметные типы описывают объекты, реестр хранит их, сервис управляет бизнес-операциями, консоль отвечает за ввод и вывод.
* **O — Open/Closed Principle.** Новые типы объектов можно добавлять через реализацию существующих интерфейсов, не переписывая общую логику отчётов.
* **L — Liskov Substitution Principle.** Реализации интерфейсов должны сохранять их ожидаемое поведение и контракты.
* **I — Interface Segregation Principle.** Разделены интерфейсы общего инвентарного объекта, транспорта и энергопотребляющего устройства.
* **D — Dependency Inversion Principle.** Сервис зависит от интерфейсов реестра и техосмотра, а консоль — от интерфейса операций с парком.

## Расширение проекта

### Добавление нового вида транспорта

Нужно создать новый тип, реализующий `InventoryItem` и `Transport`, а также определить его специфические поля и методы. Если объект потребляет энергию, он дополнительно реализует `EnergyConsumer`.

Существующие отчёты смогут обрабатывать новый тип через интерфейсы. Если у него появятся особые правила учёта, их потребуется добавить отдельно.

### Добавление сотрудников

Сотрудники не должны реализовывать `InventoryItem` и не должны попадать в реестр имущества, поскольку не являются объектами на балансе.

Для них следует создать отдельную предметную модель, интерфейс хранения и сервис управления сотрудниками. При необходимости можно добавить отдельные отчёты по персоналу.

### Добавление нескольких складов

Текущий реестр рассчитан на единый парк без распределения по местам хранения. Для поддержки нескольких складов потребуется определить модель склада или местоположения, изменить интерфейс и реализацию хранения, а также добавить операции перемещения и фильтрации объектов по складам.

После этого следует обновить отчёты и тесты, учитывая, что инвентарный номер должен оставаться уникальным в пределах всей системы, если именно такое правило установлено требованиями.

## Тестирование

Запуск всех тестов:

```bash
go test ./...
```

Подробный вывод:

```bash
go test ./... -v
```

Оценка покрытия:

```bash
go test ./... -cover
```

Тесты проверяют успешное добавление, отказ техосмотра, дубликаты номеров, пустой номер, недопустимый уровень простоты, расчёт отчётов и пустой инвентарь.

В unit-тестах техосмотр подменяется тестовой реализацией `FakeInspectionService`. Она позволяет управлять результатом проверки и считать количество вызовов, не запуская реальную реализацию.
